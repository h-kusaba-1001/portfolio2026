# Architecture Decision Records

このサイトの技術選定と、その判断理由の記録。

新しい決定を追加するときは末尾に追記し、既存の ADR は書き換えず
「Superseded by ADR-XXX」と追記して残す。

## ADR-001: デプロイ CLI に osls を採用する

**Status**: Accepted

**決定**
Serverless Framework v4 ではなく [osls](https://github.com/oss-serverless/osls)（v3 の OSS フォーク / MIT）を使う。

**背景**
Serverless Framework は v4 から、年間収益 200 万ドル超の組織が有料となり、
個人利用でもアカウント登録またはライセンスキーの入力が必須になった。

**理由**
「固定費ゼロ」という本プロジェクトの前提と噛み合わない。
osls は Bref のメンテナが作成・維持しており、Bref 公式ドキュメントも移行を推奨している。
コマンドは `serverless` のまま使えるドロップイン置き換えとして動作する。

**トレードオフ**
v4 の新機能は使えない。本プロジェクトの要件では不要と判断。

## ADR-002: データベースを持たない

**Status**: Accepted

**決定**
RDS を含むデータベースを一切使わない。コンテンツは Markdown で保持する。

**背景**
掲載内容は読み取り主体で、書き込み要件がない。

**理由**
RDS は最小構成でも月 2,000〜3,000 円かかる。本プロジェクトの主目的である
固定費削減に対して、得られるものがない。

なお固定費が跳ねる主因は RDS・NAT Gateway・ALB であり、Lambda ではない。
Lambda は完全従量課金で、この規模なら無料枠に収まる。

**トレードオフ**
将来書き込み機能が必要になった場合は DynamoDB を追加する。従量課金のまま維持できる。

## ADR-003: Markdown は S3 ではなくリポジトリに同梱する

**Status**: Accepted

**決定**
`content/` 配下に置き、デプロイパッケージに含める。

**理由**
S3 に配置すると毎リクエストで S3 API 呼び出しが挟まり、コールドスタート時の
レイテンシに効いてくる。リポジトリ同梱ならファイル読み込みだけで済む。
加えて、コンテンツの変更履歴が Git に残る。

**トレードオフ**
更新のたびにデプロイが必要。更新頻度が月数回のため許容する。

## ADR-004: サーバサイドは要件が生じるまで実装しない

**Status**: Accepted

**決定**
Laravel が現時点で担うのはルーティングとコンテンツ配信のみとする。
API・ビジネスロジックは、必要になった時点で追加する。

**理由**
掲載内容は読み取り主体で、現時点でサーバ側の処理を要する機能要件がない。
要件が無いまま層を用意しても、保守対象が増えるだけで得るものがない。

**補足**
これは「API・ビジネスロジックを持たせない」という禁止事項ではない。
要件が無いため結果として存在していない、という状態を指す。
必要が生じた時点で `serverless.yml` に関数を追加して拡張する。

なお Inertia はサーバがページコンポーネント名と props を返す仕組みのため、Laravel 層自体は必須。
薄いのはビジネスロジックであって Laravel ではない。

**トレードオフ**
「作り込んでいない」と見られる可能性がある。構成図に拡張ポイントを図示することで、
判断の結果であることを示す。

## ADR-005: 配信に Lift の server-side-website を使う

**Status**: Accepted

**決定**
CloudFront を手動構築せず、Lift プラグインの `server-side-website` 構造を使う。

**理由**
Bref 公式が推奨する構成。必要なリソースの作成と、アセットの S3 アップロードが自動化される。

**補足**
Lift・Bref・osls はいずれも Matthieu Napoli 氏によるもの。
エコシステムとして一貫しており、組み合わせの相性が担保されている。

## ADR-006: フロントエンドに React + TypeScript を採用する

**Status**: Accepted

**決定**
Inertia のフロントエンドに Vue ではなく React を使う。言語は TypeScript とする。

**TypeScript を選ぶ理由**
サーバが返す props の形（`sections[].blocks[].heading` / `html`）と、
構成図ノードの定義（`DiagramNodeDef`）が対応している。型があれば、
サーバ側の変換を変えてフロント側を直し忘れた場合にビルドで落ちる。

ただし、構成図ノードの `heading` が `content/stack.md` の H2 見出しと
一致するかどうかは型では検証できない。ここはテストで担保する。

**トレードオフ**
Vue.js 2 の方が習熟度は高い。Inertia の抽象度が高く両者の差異が小さいため許容する。

## ADR-007: ローカル開発環境は Laravel Sail で構築する

**Status**: Accepted

**決定**
ローカル開発は `php artisan serve` ではなく Laravel Sail（Docker）で行う。

**理由**
ホストの PHP・Node のバージョンに依存せず、リポジトリを clone した状態から
同じ手順で起動できる。実行環境が `docker-compose.yml` としてコードに残る。

**構成**
データベースを持たない（ADR-002）ため、Sail のサービスは PHP アプリケーションのみ。
MySQL・Redis・Meilisearch などは含めない。

**PHP バージョン**
PHP 8.4 に固定する。Sail のイメージと Bref のランタイムで同じバージョンを使い、
ローカルと本番の乖離を減らす。イメージタグは `latest` ではなくバージョンで固定する（NFR-S5）。

**本番との関係**
Sail はローカル開発専用で、デプロイ成果物には影響しない。
本番は Bref のランタイムイメージ上で動くため、実行環境は完全には一致しない。
挙動の最終確認は本番環境で行う（Bolt B-2 でデプロイを先行させる理由）。

**トレードオフ**
Docker の起動が前提になる。バージョン差異による環境依存の切り分けコストの方が高いと判断した。

## ADR-008: Inertia の SSR を導入しない

**Status**: Accepted

**決定**
Inertia SSR を導入せず、クライアントサイドレンダリングのみとする。
OGP・meta description は Blade テンプレート側で静的に出力する。

**理由**
SSR は Lambda 上に Node プロセスをもう一つ動かす構成になる。
掲載内容は数ページの静的なテキストで、検索流入を主目的にしていない。
リンクを共有したときに内容が伝わればよく、その用途は Blade で出す OGP と
meta description で満たせる。

ADR-004 と同じ判断基準。要件に対して不要な層を持たない。

**トレードオフ**
検索エンジンに本文がインデックスされない可能性がある。
JavaScript を無効にした環境では本文が表示されない。
将来 SSR が必要になった場合は、Lift の構成に Node 関数を追加して導入する。
構成図の拡張ポイントに含める余地がある。

## ADR-009: テストは Pest でユニットと Feature の 2 層に絞る

**Status**: Accepted

**決定**
Pest を使い、Markdown 読み込みなど中核ロジックのユニットテストと、
Inertia のページレンダリングを確認する Feature テストを書く。
ブラウザテスト（構成図アニメーションの動作確認）は書かない。

**理由**
壊れたときの影響が最も大きいのは Markdown → Inertia props の変換で、
ここが失敗すると全ページが表示されなくなる。この経路はテストで押さえる。

構成図アニメーションは目視で判断できる範囲であり、ブラウザテストの構築・維持コストに
見合わない。

**トレードオフ**
アニメーションの回帰は手動確認に依存する。

## ADR-010: AI-DLC の Security ベースライン拡張を有効にする

**Status**: Accepted

**決定**
AI-DLC の 3 つの拡張のうち、Security ベースラインのみ有効にする。
Resiliency ベースラインと Property-Based Testing は無効にする。

**理由**
Security: 公開する Web アプリケーションである以上、セキュリティヘッダ・最小権限 IAM・
依存の脆弱性管理は規模に関わらず必要。ポートフォリオとして公開する以上、
ここが緩いと技術力の主張と矛盾する。

Resiliency: 対象は可用性目標を持たない個人サイト。データベースも外部連携もなく、
復旧対象の状態を持たない。15 の実践領域の大半が空振りする。

Property-Based Testing: ビジネスロジックが Markdown の読み込みと変換のみで、
生成的テストが有効に働く探索空間がない。

**影響**
セキュリティ非機能要件 NFR-S1〜S7 が requirements.md に追加された。
アクセスログとログ保持（NFR-S2、NFR-S3）は NFR-1 の費用目標に対して増分になるが、
この規模では両立する見込み。

**トレードオフ**
CSP を `unsafe-inline` なしで運用する場合、Vite のビルド設定に制約が出る可能性がある。
実装時に判明したら、正当化を文書化した上で例外を認めるか、nonce 方式に切り替える。
→ ADR-011 で決着。`style-src` にのみ `'unsafe-inline'` を許可する。

## ADR-011: CSP は script を厳格に保ち、style にのみ `'unsafe-inline'` を許可する

**Status**: Superseded by ADR-018（2026-08-23）

> 許可の根拠だった「構成図が `style` 属性を書き換える」という前提が、
> 実装（`<animateMotion>`）では成立していなかった。ADR-018 で全面的に撤回した。

**決定**

```
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data:;
font-src 'self';
connect-src 'self';
frame-ancestors 'none';
base-uri 'self';
form-action 'none'
```

**背景**
SECURITY-04 は `'unsafe-inline'` を「文書化された正当化なしに使わない」と定める。
一方、本サイト最大の見せ場である構成図アニメーション（UoW-4）は、
光の粒の位置を要素の `style` 属性で更新する実装が最も素直である。
`style-src` に `'unsafe-inline'` が無いと、`style` 属性による指定はブラウザに拒否される。

**理由**
XSS の実害は、注入されたスクリプトが実行されることで生じる。
`script-src 'self'` を維持する限り、インラインスクリプトも外部スクリプトも実行されない。
`style-src` の緩和で増えるリスクは、CSS インジェクションによる表示改変や
一部の情報漏洩手法に限られる。本サイトには入力フォームもセッションも存在せず、
盗まれる対象がない。

nonce 方式（ADR-010 のトレードオフで挙げた案）は解決にならない。
nonce は `<style>` 要素には付けられるが、`style` 属性には付けられないため、
結局アニメーションの実装制約が残る。

**トレードオフ**
CSP の評価ツールでは減点される。減点を受け入れる代わりに、見せ場の実装自由度を取った。
`form-action 'none'` と `frame-ancestors 'none'` を設定できるのは、
フォームも埋め込み用途も無いからで、この 2 つは厳格側に振れている。

## ADR-012: セキュリティヘッダは CloudFront で付与し、オリジンへの直アクセスを遮断する

**Status**: **Superseded by ADR-015**（2026-08-22）

> この決定は ADR-015 により置き換えられた。
> セキュリティヘッダは Laravel のミドルウェアで付与し、オリジン遮断は行わない。
> 判断が変わった経緯は ADR-015 に記録している。
> なお、デプロイ用 IAM ポリシーに関する記述（SECURITY-06 の例外）は
> ADR-015 でも引き続き有効とする。

**決定**
セキュリティヘッダは Laravel のミドルウェアではなく、
CloudFront の Response Headers Policy で付与する。
併せて、CloudFront がオリジンリクエストに付与する共有シークレットヘッダを
Lambda 側のミドルウェアで検証し、一致しないリクエストを 403 で拒否する。

**背景**
CloudFront で付与すると、Lambda を経由しない静的アセットにもヘッダが付く。
ただし Lift の `server-side-website` 構成では、API Gateway のエンドポイントも
外部から到達可能な状態で作られる。この経路は CloudFront を通らないため、
ヘッダが付かない HTML が返る。SECURITY-04 は
「HTML を返す全てのエンドポイント」を対象とするため、この状態は非準拠になる。

**理由**
ミドルウェアでもヘッダを付ける案（二重管理）と比較して、
オリジン遮断は「ヘッダが付かない経路を消す」という根本的な対処になる。
ヘッダの管理箇所も 1 つに保てる。

副次的に、オリジン迂回による直接負荷（CloudFront のキャッシュを通さない
リクエストの流し込み）も防げる。これは ADR-013 の濫用対策とも噛み合う。

**実装上の要点**
- 共有シークレットは環境変数で供給し、コードに含めない（SECURITY-12）
- ログにシークレットの値を出力しない（SECURITY-03）
- ローカル開発時は検証を無効化する（環境変数が未設定なら素通り）

**デプロイ用 IAM についての付記**
`osls deploy` は CloudFormation 経由で未作成のリソースを操作するため、
IAM ポリシーのリソースをリソース単位で限定することが原理的に難しい。
デプロイ用ポリシーはサービス単位で限定し、リソースはワイルドカードとする。
**これは SECURITY-06 に対する意図的な例外であり、ここに記録する。**
Lambda の実行ロール（実行時の権限）は CloudWatch Logs への書き込みのみに限定しており、
そちらは最小権限を満たす。

**トレードオフ**
ローカル開発では実際のヘッダを確認できない。
Feature テストの対象は「ヘッダが付くこと」ではなく「遮断が効くこと」になる。
ヘッダそのものの検証は、デプロイ後に実 URL に対して行う。

## ADR-013: 濫用対策に WAF を使わず、キャッシュ・同時実行上限・予算アラートで代替する

**Status**: Accepted

**決定**
AWS WAF を導入しない。代わりに次の 3 つを組み合わせる。

1. CloudFront のキャッシュを強め、Lambda への到達そのものを減らす
2. Lambda の予約済み同時実行数に上限を設ける（初期値 10）
3. AWS Budgets で予算アラートを設定する（しきい値 1 USD）

**背景**
SECURITY-11 は公開エンドポイントにレート制限を求める。
一方 AWS WAF は月 5〜8 USD の固定費が発生し、NFR-1（月額 100 円以下）と正面から衝突する。

**理由**
この構成で悪用された場合の実害は、情報漏洩ではなく請求額の増加である。
公開 API も認証もデータベースも無く、攻撃者が得られるものは
「誰でも見られる HTML」だけで、奪取の対象がない。

守るべきものが費用である以上、費用に上限を設ける対策が要件に直接効く。
同時実行数の上限は、コストの増加を物理的に頭打ちにする。
WAF のレート制限は個々の送信元を絞るが、費用の総量に上限は与えない。

**トレードオフ**
同時実行数の上限に達すると、正規の閲覧者にも 429 が返る。
**可用性を犠牲にして費用を守る選択である。** 個人ポートフォリオであり、
アクセス集中時に一時的に見られないことの損失は小さいと判断した。

しきい値（同時実行数 10、予算 1 USD）は運用しながら調整する。

## ADR-014: ログ保持期間を 14 日とし、SECURITY-14 のログ保持要件を適用外とする

**Status**: Accepted

**決定**
CloudWatch Logs のロググループ、および CloudFront・API Gateway のアクセスログ
（S3 保存分）の保持期間を、いずれも **14 日**とする。

これに伴い、AI-DLC の Security ベースライン拡張のうち
**SECURITY-14 の「ログ保持は最低 90 日」という要件のみを適用対象から外す**。
SECURITY-14 の他の項目（アプリケーションにロググループの削除権限を与えない、等）は
引き続き適用する。

**背景**
ADR-010 で Security ベースラインを有効にしている。SECURITY-14 は
アプリケーションロググループの保持期間を最低 90 日と定めている。
SECURITY-06 と異なり、SECURITY-14 には例外を文書化して逸脱する規定が無い。
そのため本決定は「例外の記録」ではなく、**拡張ルールの適用範囲そのものの変更**にあたる。

**理由**
1. 個人開発のポートフォリオであり、長期のログ保管を求める監査要件・コンプライアンス要件が存在しない
2. 見返す可能性のない古いログを保持しない運用方針
3. 費用の抑制

**理由 3 についての正確な記述**
現在の想定規模（月 100 MB 程度）では、14 日と 90 日の保存料の差は
**月 1 円程度**にとどまる。したがって現時点で費用が主たる根拠として成立するわけではない。
一方、アクセスが大きく増えた場合にはログ量が費用の主要な増加要因になり、
14 日のライフサイクル削除はその上限として働く。
**費用は「現在の削減効果」ではなく「増加時の上限」として意味を持つ。**

**トレードオフ**
障害や不審なアクセスに 2 週間より後に気付いた場合、原因調査に使える記録が残らない。
このサイトは技術構成の判断を訴求の中心に置いているため、
「セキュリティ要件を緩めた」という判断そのものも記録として残す。

**再検討の条件**
- サイトに閲覧者の情報を扱う機能が加わった場合
- 実際に調査が必要な事象が発生し、14 日では足りなかった場合

## ADR-015: セキュリティヘッダは Laravel のミドルウェアで付与する（ADR-012 を置き換え）

**Status**: Accepted

**決定**
セキュリティヘッダ（NFR-S1）は Laravel のミドルウェア `SecurityHeaders` で付与する。
CloudFront の Response Headers Policy は使わない。
オリジン（API Gateway）への直アクセス遮断も行わない。

**この決定に至った経緯**

当初は次の順で判断が積み上がった。

1. ヘッダを CloudFront で付与することにした（静的アセットにも付くため）
2. その結果、API Gateway に直接アクセスされるとヘッダの付かない HTML が返る経路が残った
3. これは SECURITY-04（HTML を返す全エンドポイントにヘッダを設定すること）に対する非準拠
4. 解消のため、共有シークレットによるオリジン遮断を決めた（ADR-012）
5. しかしその実現手段が Lift の対応状況に依存し、実装量が最大になった

**見落としていたこと**

SECURITY-04 の対象は「**HTML を返すエンドポイント**」であり、
静的アセット（JS / CSS / 画像）は対象に含まれない。
HTML を返す経路は必ず Lambda を通るため、
**ミドルウェアでヘッダを付ければ、それだけで SECURITY-04 に準拠する。**

CloudFront で付与する動機は「静的アセットにも付けたい」だったが、
それは要件ではなく上乗せだった。上乗せを満たそうとした結果、
要件そのものに穴が空き、その穴を塞ぐためにオリジン遮断という重い対策を導入していた。

**理由**
- 実装は `SecurityHeaders` ミドルウェア 1 つで済む
- ローカル開発でも Feature テストでもヘッダを検証できる（CloudFront 依存だと検証できない）
- ADR-004 の判断基準（要件が無い層は作らない）と整合する

**トレードオフ**

1. **静的アセットにはセキュリティヘッダが付かない**
   SECURITY-04 の対象外であり、要件上の問題はない。

2. **API Gateway の URL に直接アクセスすると CloudFront のキャッシュを迂回できる**
   Lambda の実行回数が増える経路が残る。ただし同時実行数の上限（ADR-013）により
   費用は頭打ちになるため、実害は限定的。
   **これは既知の未対応事項として残し、構成図の拡張ポイントに含める。**
   対策が必要になった時点で、共有シークレットによるオリジン遮断（ADR-012 の方式）を導入する。

**この ADR を残す理由**
ADR-012 を書き換えず Superseded として残しているのは、
「上乗せの要件を追ったせいで本来の要件に穴を空け、重い対策で塞ごうとした」
という判断の経緯自体が、記録として価値を持つため。

## ADR-016: 同時実行数の上限はアカウント上限に委ねる（ADR-013 の補足）

**Status**: Accepted

**決定**
Lambda の予約済み同時実行数（`reservedConcurrency`）を設定しない。
アカウントの同時実行上限をそのまま費用の天井として使う。

**背景**
ADR-013 で「予約済み同時実行数を 10 に設定して費用を物理的に頭打ちにする」と決めたが、
初回デプロイで CloudFormation が次のエラーを返した。

```
Specified ReservedConcurrentExecutions for function decreases account's
UnreservedConcurrentExecution below its minimum value of [10].
```

このアカウントの上限を確認したところ、次の状態だった。

```json
{ "ConcurrentExecutions": 10, "UnreservedConcurrentExecutions": 10 }
```

新規 AWS アカウントの初期値は 10。10 を予約すると未予約分が 0 になり、
AWS が要求する「未予約分は最低 10」を割るため拒否される。
**このアカウントでは、いかなる値でも関数単位の予約ができない。**

**理由**
ADR-013 の目的は「費用の総量に上限を与えること」であって、
予約済み同時実行数という手段そのものではない。
アカウント上限が 10 である以上、**同時に 10 を超えて課金が発生することはない。**
求めていた天井は、より上位のレイヤで既に存在していた。

**再検討の条件**
AWS はアカウントの利用実績に応じて同時実行上限を自動的に引き上げる。
上限が引き上げられた時点で、この天井は失われる。
そのときは関数単位の予約（`reservedConcurrency`）を設定し直す。

**トレードオフ**
上限の引き上げは AWS 側の判断で起きるため、こちらが気付かないうちに天井が外れる。
検知は AWS Budgets の予算アラート（ADR-013）に依存する。
`aws lambda get-account-settings` で現在値を確認できる。

## ADR-017: HTML のキャッシュ TTL を 5 秒にする

**状態**: 採用（2026-08-23）

**決定**
CloudFront の既定ビヘイビアに独自のキャッシュポリシー（MinTTL 0 / DefaultTTL 5 / MaxTTL 5）を当て、
アプリ側は成功した GET・HEAD 応答に `Cache-Control: public, max-age=5` を返す。

**背景**
Lift は既定ビヘイビアに AWS 管理ポリシー `CachingDisabled` を適用する。
そのためアプリが `Cache-Control` を返しても無視され、全リクエストが Lambda に届いていた（P-2）。
U1-PF-4 は当初 60 秒を想定していた。

**なぜ 60 秒ではなく 5 秒か**
キャッシュの目的は Lambda 呼び出し回数の削減（費用と濫用対策）である。
削減効果の大半は「キャッシュ無し → 5 秒」の時点で得られる。
5 秒でも 1 エッジあたりの Lambda 到達は 0.2 回/秒に落ちる。
そこから 60 秒へ伸ばして得られる差は小さく、
**費用の天井はアカウントの同時実行上限 10（ADR-016）が既に担保している。**

CloudFront のキャッシュはエッジロケーション単位のため、
散発的なアクセスでは TTL を伸ばしてもヒット率は上がらない。
TTL が効くのは同一エッジへの連続アクセス、すなわちリロードと濫用であり、そこは 5 秒で足りる。

**5 秒を選ぶもう一つの理由**
`versionedAssets` を有効にしていないため、デプロイで古いアセットが消える。
HTML を長くキャッシュすると、消えた JavaScript を指したままの HTML が配信され画面が壊れる。
**TTL 5 秒なら、その窓が実質無視できる。**

**なぜ `CachingOptimized` を使わないか**
`CachingOptimized` は DefaultTTL が 1 日である。
オリジンが `Cache-Control` を返し損ねた瞬間に 1 日キャッシュされる。
MaxTTL を 5 秒で固定できる独自ポリシーの方が、事故の上限が小さい。

**キャッシュキー**
クッキーとクエリ文字列は含めない。`X-Inertia` ヘッダのみ含める。
現状 Inertia のクライアント遷移は使っていないが、将来 `<Link>` を入れると
同じ URL に対して HTML と JSON が返り分かれる。後から気付くと混線事故になるため先に入れてある。

**トレードオフ**
デプロイ結果が最大 5 秒遅れて見える。実用上は問題にならない。

## ADR-018: CSP から `'unsafe-inline'` を完全に除去する（ADR-011 を Superseded）

**状態**: 採用（2026-08-23）

**決定**
本番の `style-src` を `'self'` のみにする。CSP から `'unsafe-inline'` が完全に消える。
ローカルのみ Vite の HMR のために `'unsafe-inline'` を残す。

**背景**
ADR-011 で `style-src 'unsafe-inline'` を許可した理由は
「構成図のアニメーションが `style` 属性を書き換えるため」だった。
**しかし実装では `<animateMotion>`（SVG のネイティブ機能）を使ったため、
この前提は成立していなかった。** 許可した理由が最初から存在しなかったことになる。

**実施したこと**
アプリ側に残っていた `style` 属性を全て排除した。

| 箇所 | 変更前 | 変更後 |
|---|---|---|
| `DiagramNode` / `ArchitectureDiagram` の文字 | `style={{ fontSize, fontWeight }}` | SVG のプレゼンテーション属性 `fontSize` / `fontWeight` |
| `Career` の丸と見出し | index から幅・不透明度・文字サイズを計算して `style` に渡す | 静的な Tailwind クラスの配列（`PERSPECTIVE`）から選ぶ |

`Career` の変更には副次的な利点がある。
**以前は項目が増えると既存の項目の見え方まで変わっていた**（比率で計算していたため）。
最新から数えた段階で決まるようになり、転職して項目が増えても過去の見え方が変わらない。

**確認したこと**
- ソース全体に `style={{` が 1 つも残っていないこと
- `.style.` への代入や `setAttribute('style')` が無いこと
- Markdown 側に `style` 属性が無いこと
- ビルド成果物中の `createElement('style')` は
  React 19 の `<style precedence>` 用の経路であり、この実装では通らないこと

**残るリスク**
ブラウザテストを書かない方針（ADR-009）のため、
**実ブラウザで CSP 違反が出ないことは目視でしか確認できない**（backlog B-4）。
万一スタイルが壊れた場合、`config/security.php` の 1 行を戻せば復旧できる。

**トレードオフ**
動的なスタイルを足したくなったとき、静的クラスで表現する必要がある。
このサイトの規模では制約にならない。

## ADR-019: 欧文フォントだけを同梱してセルフホストする

**状態**: 採用（2026-08-23）

**決定**
IBM Plex Sans / IBM Plex Mono の**欧文サブセットのみ**をリポジトリに同梱し、
自分のオリジンから配信する。和文フォントは持たず、システムフォントに任せる。

**背景**
書体がシステムフォント任せで、ページに人格が無かった。
一方で外部の CDN からフォントを読むと、
`font-src 'self'`（ADR-011 / ADR-018）と
「外部リソースを読み込まない」方針（SECURITY-13）の両方に反する。

**やり方**
`resources/fonts/` に woff2 を置き、`app.css` の `@font-face` から相対パスで参照する。
Vite が `/build/assets/` にハッシュ付きで出力するため、
`serverless.yml` の `'/build/*'` でそのまま配信され、**新しい割り当ては要らない**。

`unicode-range` を欧文に限っているので、**日本語は自動的に次のシステムフォントへ落ちる。**
和文フォントは数 MB になるため持たない。この構成なら合計 80 KB で済む。

| ファイル | 用途 | サイズ |
|---|---|---|
| `ibm-plex-sans-latin.woff2` | 可変フォント。400〜600 を 1 ファイルで | 45.7 KB |
| `ibm-plex-mono-400-latin.woff2` | ラベル・コード | 14.7 KB |
| `ibm-plex-mono-500-latin.woff2` | ラベルの強調 | 14.9 KB |

**なぜ IBM Plex か**
和文はシステムフォント（ヒラギノ・Noto Sans JP など）で表示されるため、
**欧文はそれと並んでも浮かない書体である必要がある。**
Plex は Sans と Mono が同じ骨格で設計されており、
1 行の中で混ぜても崩れない。技術文書のために作られた書体という出自も題材に合う。

**トレードオフ**
初回表示でフォントの読み込みが入る。`font-display: swap` にしているため
文字が消える時間は発生せず、システムフォントで先に表示されて後から差し替わる。
