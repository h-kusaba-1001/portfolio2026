# Performance Test Instructions

## 結論: 負荷テストは実施しない

**理由**: このプロジェクトには**性能目標が存在しない。**

| 要件 | 内容 |
|---|---|
| U1-PF-5 | **コールドスタート時間の数値目標は設けない** |
| U1-SC-3 | 想定負荷はピークで数リクエスト/秒。**容量計画を行わない** |
| U1-AV-1 | 稼働率の目標値を設定しない |

計測要件そのものを INCEPTION 段階で削除している（`docs/requirements.md` の NFR-4 削除の経緯）。
**目標が無いものを測っても合否が判定できない。**

さらに、**負荷をかけること自体が要件と衝突する**。
アカウントの Lambda 同時実行上限が 10 であり（ADR-016）、
これが費用の天井として機能している。負荷テストは
① この天井にすぐ当たって意味のある数字が取れない
② 意図的に課金を発生させる
の 2 点で、NFR-1（月額 100 円以下）に反する。

## 代わりに把握していること（実測値）

| 項目 | 実測 | 取得方法 |
|---|---|---|
| Lambda 実行時間 | **18.8 ms** | CloudWatch Logs の REPORT 行 |
| Lambda 使用メモリ | **138 MB / 512 MB** | 同上 |
| デプロイパッケージ | 16 MB | `osls deploy` の出力 |
| フロントのバンドル | JS 330 kB（gzip 105 kB）/ CSS 42 kB（gzip 8 kB） | `npm run build` |
| ビルド時間 | 0.6 秒 | 同上 |
| テスト実行時間 | 0.8 秒 | `pest` |

**メモリは 512 MB に対して 138 MB。** 引き下げる余地はあるが、
メモリを削ると CPU 割り当ても減って実行時間が延びるため、
費用が下がるとは限らない。**実測せずに触らない。**

## 性能を気にすべき状況（そのときに測る）

| 状況 | 測るもの | 方法 |
|---|---|---|
| CloudWatch で `Throttles` が観測された | 同時実行の上限到達 | メトリクスを確認し、上限の引き上げを検討 |
| 請求額が予算アラート（1 USD）を超えた | どのサービスが伸びたか | Cost Explorer |
| コールドスタートが体感で遅い | `Init Duration` | CloudWatch Logs の REPORT 行 |
| バンドルが目に見えて重くなった | 依存の内訳 | `npx vite-bundle-visualizer` 等 |

## 記録として

**「性能目標を持たない」ことも設計判断である。**
数字を掲げると、それを守るための作り込み（プロビジョンド同時実行など）が要求され、
固定費ゼロという前提と衝突する。**目標を置かないことで、置かない選択が取れる。**
