## R-1. 分割規則（Markdown → Section）

入力を上から順に走査し、次の 3 つに振り分ける。

| 位置 | 振り分け先 |
|---|---|
| 最初の H1 | `title`（**HTML には含めない**: Q3 = A） |
| 最初の H2 より前の本文 | `lead` |
| 各 H2 とその配下 | `ContentBlock`（見出しは `heading` / `key`、本文は `html`） |

**細則**

| # | 規則 |
|---|---|
| R-1-1 | H1 が複数ある場合、**最初の 1 つ**を `title` とし、2 つ目以降は本文として扱う |
| R-1-2 | H1 が無い場合、`title` は `SectionId` の既定タイトルを使う（Q2 = C） |
| R-1-3 | H2 の配下は、**次の H2 または文書末尾まで**。H3 以下は配下に含める |
| R-1-4 | H2 が 1 つも無い場合、本文は全て `lead` に入り、`blocks` は空配列になる（失敗ではない） |
| R-1-5 | H1 より前に本文がある場合、それも `lead` に含める |
| R-1-6 | `lead` が空文字になることは許容する（H1 の直後がいきなり H2 のファイル） |

**実データへの適用結果**

| ファイル | `title` | `lead` | `blocks` |
|---|---|---|---|
| `stack.md` | 技術構成 | 導入文（3 行） | 6 個 |
| `career.md` | キャリアの変遷 | 導入文（3 行） | 4 個 |
| `experience.md` | やってきたこと（抜粋） | 箇条書き全体 | **0 個** |
| `next.md` | これから | 本文全体 | **0 個** |

## R-2. 見出しの正規化規則（照合用キーの生成）

Q5 = B。**表示には使わない。照合にのみ使う。**

適用順序:

| 順 | 処理 |
|---|---|
| 1 | 前後の空白を除去（半角空白・タブ・改行・**全角空白 U+3000**） |
| 2 | 文字列中の連続する空白を、半角空白 1 つに畳む（全角空白も半角として扱う） |
| 3 | 英字を小文字に変換（**ASCII のみ**。日本語やその他の文字は変えない） |

**変換例**

| 原文 | キー |
|---|---|
| `CloudFront` | `cloudfront` |
| `  API　Gateway  `（全角空白入り） | `api gateway` |
| `Lambda (Bref)` | `lambda (bref)` |
| `デプロイ: osls` | `デプロイ: osls` |

**やらないこと**（意図的に除外）

- 記号の除去（`(` `)` `:` `+` `.` はそのまま残す）
- 全角英数字 → 半角英数字の変換
- Unicode 正規化（NFKC 等）

**理由**: 吸収範囲を広げるほど「何が一致するか」が読み手に予測できなくなる。
上の 3 つは「見た目が同じなら一致する」と直感に合う範囲に留めた。

### ⚠️ R-2 の重大な注意

**この正規化規則は、サーバ（PHP）とフロント（TypeScript）の両方で同じ結果を出す必要がある。**

構成図のノード定義（`DiagramNodeDef`）はフロント側にあり（Q7 = A / UoW-4）、
そこに書かれた見出しを同じ規則で正規化しないと照合できない。
**2 箇所に同じロジックを持つことになり、ずれると実行時まで気付けない。**

**緩和策**（UoW-4 で必ず実施すること）

1. 全ノードの `key` が `stack.md` の `blocks` に実在することを検証するテストを置く
2. 一致しないノードでは「この要素の説明はまだありません」を表示し、画面を壊さない
3. ノード定義を PHP からも読める形（JSON 等）に置くことを検討する
   → そうすればテストが両者を突き合わせられる

## R-3. 失敗判定の規則

Q4 = C。**次のいずれかに当てはまる場合のみ失敗**とする。

| # | 条件 | 理由の種別 |
|---|---|---|
| R-3-1 | ファイルが存在しない | `FILE_MISSING` |
| R-3-2 | ファイルが読めない（権限等） | `FILE_UNREADABLE` |
| R-3-3 | **H1 を除いた本文が空**（空白のみを含む） | `BODY_EMPTY` |
| R-3-4 | HTML 変換で例外が発生した | `CONVERSION_FAILED` |

**失敗としないもの**（誤検知を避けるため明示）

| 状況 | 判定 |
|---|---|
| H2 が 1 つも無い | **成功**（R-1-4） |
| `lead` が空だが H2 ブロックはある | **成功**（R-1-6） |
| H1 が無い | **成功**（既定タイトルにフォールバック: R-1-2） |
| ブロックの `html` が空（見出しだけの H2） | **成功**（空ブロックとして保持） |

**失敗時の振る舞い**

1. `ContentUnavailable` を投げる（取得層）
2. ユースケース層が捕捉し、`Section::failed()` に差し替える
3. 失敗をログに記録する（セクション ID・理由の種別・例外クラス名）
4. **例外を外に伝播させない。** 他のセクションの処理を続ける
5. 画面はセクションの枠を残し、本文の位置に固定文言を表示する（Q6-a = A）

**ログに出さないもの**: ファイルの絶対パス、ファイルの中身（NFR-S6 / SECURITY-09）。

## R-4. HTML 変換の規則（セキュリティ）

| # | 規則 | 根拠 |
|---|---|---|
| R-4-1 | Markdown 中の**生 HTML は除去する**（`html_input = strip`） | 変換結果を `dangerouslySetInnerHTML` に渡すため |
| R-4-2 | 危険なスキームのリンク（`javascript:` 等）を拒否する（`allow_unsafe_links = false`） | SECURITY-05 の考え方をコンテンツ経路に適用 |
| R-4-3 | 入れ子の深さに上限を設ける（`max_nesting_level`） | 異常な入れ子による処理時間の増大を防ぐ |
| R-4-4 | 変換結果に `<script>` `<iframe>` `<object>` `<embed>` が含まれないこと | R-4-1 の結果として満たされる。**テストで固定する** |

**現時点のコンテンツは自前のもののみ**だが、`content/` は「コードを触らずに更新できる」入り口
（US-7）であり、将来的に他人の手が入る可能性を排除できない。
**自前だから安全、とは考えない。**

## R-5. 順序の規則

| # | 規則 |
|---|---|
| R-5-1 | セクションの表示順は `SectionId::inDisplayOrder()` が定める（技術構成 → やってきたこと → キャリア → これから） |
| R-5-2 | ブロックの順序は **Markdown 中の H2 の出現順**を保つ |
| R-5-3 | ファイルシステムの列挙順に依存しない（`glob` の結果順で並べない） |

## R-6. キャッシュの規則

Q7 = A（セクション単位）。判断の経緯は business-logic-model.md §5 に記載。

| # | 規則 |
|---|---|
| R-6-1 | キャッシュキーはセクション ID とファイル更新時刻から作る（`content:{id}:{mtime}`） |
| R-6-2 | TTL は設けない。ファイルが更新されればキーが変わり、自然に失効する |
| R-6-3 | **失敗はキャッシュしない。** 次のリクエストで再試行できるようにする |
| R-6-4 | ファイル更新時刻が取得できない場合（ファイル不在）は、キャッシュを引かずに委譲する |
| R-6-5 | ローカル開発ではキャッシュを無効化できること（設定で切り替え） |

## R-7. 未知ファイルの規則

Q6 = A。

| # | 規則 |
|---|---|
| R-7-1 | `SectionId` に定義されていないファイルは読まない |
| R-7-2 | ディレクトリ内の列挙を行わない（`SectionId` から直接パスを組み立てる） |
| R-7-3 | セクションを増やすときは `SectionId` にケースを追加する（コード変更が必要） |

**R-7-2 の副次的な効果**: ファイル名が enum に閉じているため、
外部入力からパスを組み立てる経路が存在しない（パストラバーサルの余地がない）。
